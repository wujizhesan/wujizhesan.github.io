睦子：一次从 QAPI 到 QChrome 的双管线重建

2026-08-14
2026-08-14
985
4m
逆向工程
VueReactElectronAST

睦子项目最早遇到的问题不是代码，而是产品边界不清。

对标产品看起来像一套客服工具，实际包含知识库平台、聚合浏览器和 Windows 桌面组件。把它们混在一起时，页面、接口和桌面行为会互相干扰；确认 QAPI、QChrome、QWIN 是三个独立组件后，整个项目才被拆成两条清晰的工程管线。

QAPI：知识库与管理后台 ​

QAPI 部分使用 Vue 3、Element Plus 和 Python 后端。重建过程不是逐页照着截图手写，而是从 bundle 中提取组件与路由，再将 VNode 表达转换为可维护模板。

text
原始 bundle
  → AST 提取
  → VNode 转模板
  → 特殊页面重写
  → 路由与接口接入
  → 构建和运行验证

当前管理后台共有 29 条主要路由，均完成 HTTP 访问检查。部分页面能直接从原组件结构转换，复杂页面则需要展开压缩逻辑或重新组织模板。这个过程让我意识到，所谓“自动转换”并不是追求 100% 无人干预，而是把大量重复劳动交给管线，再把人的注意力留给真正复杂的 10%。

QChrome：聚合浏览器桌面端 ​

QChrome 是另一套技术栈：React、Ant Design 与 Electron。它包含多账号主页、设置窗口、账号编辑、AI 对话日志、线索查看和浏览器多标签管理等界面，同时还有大量主进程模块。

这一部分的流程是：

text
ASAR 解包
  → chunk 格式化与组件定位
  → React 页面重建
  → 主进程模块更新
  → 品牌配置修正
  → Vite 构建
  → ASAR 重新打包

当前使用的目标版本是 v1.13.0。重打包后的 ASAR 约 143MB，包含一万四千多个条目。前端构建已通过，桌面端也完成了品牌配置和主要模块更新。

为什么必须保留两条管线 ​

QAPI 和 QChrome 的共同点是它们属于同一产品，但它们的编译产物、运行时和验证方式完全不同。

QAPI 更关注 Vue 模板、路由、接口与 DOM；QChrome 还必须处理 Electron 主进程、窗口生命周期、浏览器标签与本地配置。如果强行合并成一套转换逻辑，最后只会得到大量条件分支和无法复用的补丁。

质量门 ​

睦子项目逐渐形成了明确的完成顺序：

  1. 构建通过。
  2. API 与路由检查。
  3. 浏览器运行时检查。
  4. DOM 与截图对比。
  5. 桌面端重新打包。

尤其是截图对比前，必须关闭 canvas 动画和 transition。曾经同一个页面因为动画帧不同，像素差异被放大了上千倍。对比工具没有错，错的是输入并不稳定。

当前状态 ​

QAPI 的 29 条路由与 QChrome v1.13.0 均已完成构建，两个组件能够独立工作。后续重点不再是继续堆页面，而是维护管线、核验真实接口，并把特殊页面的手工改动逐步沉淀回转换器。

睦子让我真正理解了一件事：逆向工程里的架构设计，不是重新发明产品，而是把原产品已经存在的边界看清楚。
