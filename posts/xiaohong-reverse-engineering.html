小红：WPF 双壳、WebView2 与 612 条后端路由

2026-08-14
2026-08-14
964
4m
逆向工程
WPFWebView2FastAPIVue

小红对标的是一套电商运营工具。原产品包含两个桌面应用：工具箱和店铺管家。它们都使用 WPF 外壳承载 WebView2 页面，再通过宿主对象与本地服务完成浏览器和业务操作。

如果只复制网页，很多按钮会因为缺少 window.chrome.webview.hostObjects 而失效；如果只反编译 WPF，又会得到一个没有业务页面的空壳。小红的重点因此不是某个单独界面，而是把桌面壳、前端、桥接层和后端一起恢复。

系统分层 ​

text
WPF 桌面壳
  → WebView2 前端
  → Host Object / HTTP Bridge
  → FastAPI 后端
  → SQLite 与浏览器会话

两个 WPF 壳来自程序集反编译与工程恢复，前端则包含两套不同用途的管理界面。后端按通用业务、平台接口与具体功能分层，避免把所有端点堆进单个文件。

612 条路由意味着什么 ​

当前后端已经把 612 条路由登记并接入，包括多版 API、复制搬家、导出和管理后台接口。这个数字说明接口表覆盖较完整，但不能直接等同于 612 个真实业务闭环。

我会把路由状态分成三类：

  • 已接真实本地存储与业务逻辑
  • 已对齐输入输出结构，但仍依赖外部登录态
  • 只用于前端不崩溃的兼容接口

例如店铺、商品、订单和菜单已经可以通过本地数据完成完整页面交互；而平台真实数据仍需要有效浏览器登录态。把这两种状态写清楚，比简单说“接口都完成了”更准确。

WebView2 是关键边界 ​

纯浏览器里测试页面时，宿主对象不存在。为方便开发，前端可以提供受控降级路径；但最终验证必须回到 WPF 的 WebView2 环境，因为只有那里才有真实的宿主桥接和窗口生命周期。

这也解释了为什么“浏览器访问正常”并不能代表桌面产品已经可用。小红的验证需要同时覆盖：

  1. WPF 窗口能否启动。
  2. WebView2 是否正确加载前端。
  3. 宿主调用能否进入桥接层。
  4. 后端返回格式是否匹配前端预期。
  5. 登录态存在时，平台数据能否真正流通。

当前成果与限制 ​

目前双 WPF 工程可以编译，主要管理页面可以导航，菜单和部分业务流程已经具备本地持久化。平台浏览器守护进程与会话导入链路也已经搭好。

仍未完成的部分包括安装包与绿色版交付，以及依赖有效登录态的真实平台数据验证。这里不能用测试数据替代结论：没有活跃会话，就只能确认桥接和数据结构，不能声称线上业务已跑通。

小红项目最重要的经验，是把“桌面壳”“网页”“桥接”和“真实业务”拆成四层分别验证。只要其中一层被省略，最终都会在用户点击按钮时暴露出来。
