网店魔盒是一套 .NET 桌面应用。当前已经保留安装包、解包目录、运行文件、反编译源码和一份带 XAML/BAML 资源映射的工程结构。

从项目文件可以确认，它以 .NET 8 的 Windows Desktop SDK 为基础，目标为 x64 WPF 应用，并开启了不安全代码。程序集约 30MB，旁边还带有 WebView2、V8、SQLite 加密组件和多个运行时依赖。

## 从依赖推测架构

| 依赖或资源 | 可能承担的职责 |
| --- | --- |
| WPF / BAML | 原生窗口、页面与控件资源 |
| WebView2 | 承载网页或混合业务界面 |
| ClearScript V8 | 在 .NET 内执行 JavaScript |
| SQLite / SQLCipher | 本地数据与加密存储 |
| SignalR Client | 实时消息或状态同步 |
| Costura | 将大量依赖嵌入主程序集 |

这里使用“可能”是因为依赖存在只能证明能力被打包，不能直接证明每项功能都在主流程中使用。下一步还需要从入口、调用图和运行时行为交叉验证。

## 已恢复的代码分层

反编译工程中已经能看到 API、配置、下载、模型、视图、ViewModel、主题与工具模块。界面资源包含登录、注册、重置密码、店铺、工具、客服、分享和充值等页面。

这让后续分析不再只面对一个大型 DLL，而是可以按 MVVM 结构逐层阅读：

```text
Window / View
  → ViewModel
  → API Handler
  → Model / Config
  → 本地或远程服务
```

## “可读工程”与“可构建工程”的距离

自动反编译生成的项目文件包含大量嵌入资源和依赖声明，但仍可能存在无效标识符、丢失的 XAML 语义、资源名编码和反编译器生成的占位文件。

因此当前结论只是：

- 安装层已经解包
- 主程序集和依赖已分离
- C# 类型与主要模块可以阅读
- BAML/XAML 资源结构已经提取
- 尚未完成完整重编译和运行验证

后续应先建立最小构建基线，再逐步恢复登录窗口和主窗口，不应一次性修复整个工程。每恢复一条页面链，都要同时验证资源加载、ViewModel 绑定和 API 行为。

网店魔盒项目提醒我：反编译的终点不是得到很多 `.cs` 文件，而是重新建立“代码—资源—运行时”之间的关系。
