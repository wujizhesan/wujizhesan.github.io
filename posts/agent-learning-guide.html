我是怎么做 MeiCode 的：一个终端 AI Agent 的设计与实现

2026-08-13
2026-08-13
5.3k
21m
项目
MeiCodeAIAgentTypeScript多智能体

准备整理这个项目时，我重新翻了一遍 MeiCode 的代码。最开始做它，我想解决的问题其实很简单：能不能让模型不只是在对话框里给建议，而是进入终端，真正读取项目、修改文件、运行命令，并把结果交付出来？

真正开始写以后，我才发现“调用模型”只是最容易的一层。麻烦的是后面这些问题：工具失败了怎么办？模型一直重复同一个动作怎么办？上下文塞满了怎么办？多个 Agent 同时改代码，谁来处理冲突？一条危险命令应该由谁批准？

MeiCode 就是在解决这些问题的过程中慢慢长出来的。

项目源码放在 GitHub：wujizhesan/meicode。

先用一句话介绍 MeiCode ​

MeiCode 是一个用 TypeScript 编写的终端 AI 编程助手。它运行在 Node.js 上，终端界面使用 Ink，能够调用文件、命令、代码搜索和浏览器等工具，也支持 Skill、Workflow、MCP、子 Agent 和多智能体团队。

如果是在面试中，我会把它概括成：

我做了一个终端 Agent 运行时。它不仅封装模型请求，还负责工具调度、上下文压缩、权限审批、任务恢复和多智能体协作，并用 Git worktree 隔离不同成员的代码修改。

这里我故意用了“运行时”这个词。因为 MeiCode 不只是一个 API 客户端，它要负责 Agent 从接收任务到产生可验证结果的完整生命周期。

项目大致长什么样 ​

核心目录没有刻意做复杂分层，基本按照能力划分：

text
src/
├── agent/       主循环、事件流和系统提示词
├── tools/       文件、命令、搜索、浏览器等工具
├── context/     上下文估算、压缩和溢出落盘
├── permission/  权限规则、黑名单和路径围栏
├── provider/    OpenAI / Anthropic 协议适配
├── team/        多智能体任务、邮箱和成员管理
├── workflow/    声明式工作流和阶段状态机
├── worktree/    Git worktree 创建、合并和清理
├── hook/        生命周期 Hook
├── tui/         Ink 终端界面
└── commands/    /mode、/team、/workflow 等命令

从一次用户输入到最后输出，主要链路是：

text
用户输入
  → TUI / CLI
  → Agent Loop
  → Provider 请求模型
  → 模型返回文本或工具调用
  → 权限检查
  → 工具执行
  → 结果写回历史
  → 下一轮模型请求
  → 测试或产物验证

周围还有上下文管理、Hook、会话历史和团队系统。它们不改变主循环的方向，但会在关键节点介入。

Agent Loop：项目真正的主干 ​

Agent 的基本循环并不神秘。模型返回工具调用，程序执行工具，再把结果送回模型。只要模型还需要工具，这个过程就继续。

在 MeiCode 中，这部分集中在 src/agent/loop.ts。简化后大概是这样：

ts
for (let round = 1; round <= maxIterations; round++) {
  const messages = buildMessages(history)
  const calls = []
  let text = ''

  for await (const event of provider.streamChat(messages, options)) {
    if (event.type === 'text') text += event.text
    if (event.type === 'tool_call') calls.push(event)
  }

  if (calls.length === 0) {
    return { reason: 'complete', text }
  }

  history.push(toAssistantMessage(text, calls))
  const results = await executeBatch(calls)
  history.push(...toToolMessages(results))
}

这段伪代码能跑通，但离“能长期使用”还有很大距离。MeiCode 的主循环后来又增加了取消、流式事件、重复调用检测、上下文超限恢复、工具连续失败止损和团队任务等待。

为什么一定要把工具结果写回历史 ​

模型发出的 assistant(tool_calls) 和工具返回的 tool 消息必须配对。如果中途取消、异常退出或错误恢复时只留下前半段，下一次请求可能直接被 Provider 拒绝。

我遇到过的一个实际问题就是：历史中残留了不完整的工具调用，DeepSeek 协议返回 400。最后我在每次请求前加了一层 sanitizeMessages，过滤无法配对的消息。

这个问题很适合在面试里讲，因为它说明 Agent 的状态不是普通聊天记录。它更像一份需要满足协议约束的执行日志。

事件流和执行逻辑为什么分开 ​

终端界面需要实时显示文本、思考状态、工具结果和 Token 用量，但我不希望 Agent Loop 依赖 Ink。

所以主循环对外暴露 AsyncIterable<AgentEvent>：

ts
type AgentEvent =
  | { type: 'text'; text: string }
  | { type: 'thinking'; text: string }
  | { type: 'tool_result'; name: string; success: boolean }
  | { type: 'usage'; inputTokens: number; outputTokens: number }
  | { type: 'done'; reason: string }

TUI 只消费事件，不参与推理。无人值守模式也可以复用同一个循环，只是换一种事件消费者。这让核心执行逻辑和展示层保持独立。

用户按下 Ctrl+C 时，外部通过 AbortController 取消当前请求。Provider 和 Agent Loop 使用同一个 AbortSignal，避免界面已经退出，模型流还在后台继续跑。

工具系统：不是“让模型执行一段字符串” ​

MeiCode 中每个工具都实现同一个接口：

ts
interface Tool {
  name: string
  description: string
  parameters: JsonSchema
  execute(
    args: Record<string, unknown>,
    ctx: ToolContext,
  ): Promise<ToolResult>
}

interface ToolResult {
  success: boolean
  output: string
  truncated?: boolean
  error?: string
}

ToolRegistry 负责注册工具，并把它们转换成模型可以识别的 function calling 描述。模型只负责选择工具和生成参数，真正执行仍由本地程序完成。

这样做有几个好处：

  • 所有工具共享相同的权限入口
  • 错误可以结构化返回，而不是伪装成普通文本
  • TUI 能统一显示工具状态
  • Skill 可以限制允许使用的工具集合
  • 测试时可以替换成假的 ToolRegistry

读并发，写串行 ​

模型一轮可能返回多个工具调用。如果它要同时读取几个文件，没有必要一个个等待；但如果同时编辑两个文件，或者一边写文件一边运行命令，并发顺序可能导致不可预测的结果。

MeiCode 的做法是把调用分成两组：

ts
const reads = calls.filter((call) => READ_ONLY_TOOLS.has(call.name))
const others = calls.filter((call) => !READ_ONLY_TOOLS.has(call.name))

const readResults = await Promise.all(reads.map(executeOne))

for (const call of others) {
  await executeOne(call)
}

这是一个很小的设计，但效果很实际：读操作获得并行速度，写操作保留确定性。

它也不是绝对最优。例如两个写入完全不同文件的操作理论上可以并发，但判断依赖关系本身也有成本。当前版本选择了更容易解释和恢复的策略。

兼容不同模型的参数习惯 ​

不同模型对工具参数的命名并不总是一致。同一个路径，有的模型会生成 path，有的会生成 file_path 或 filepath。

我没有让每个工具分别处理这些差异，而是在进入权限检查和工具执行前统一归一化：

ts
const ARG_ALIASES = {
  path: ['file_path', 'filepath', 'target', 'file'],
  command: ['cmd', 'command_line', 'shell_command'],
  content: ['text', 'body', 'data'],
  pattern: ['glob', 'search', 'query'],
}

这类兼容层看起来不“高级”，却是多模型切换时非常容易踩到的坑。

防止 Agent 把自己跑死 ​

Agent 是循环系统，只要停止条件设计得不好，它就可能一直消耗 Token。

MeiCode 做了几层止损。

最大轮数 ​

每次任务有 maxIterations。到达上限后，无论模型是否认为完成，循环都会结束。

剩余轮数较少时，系统会提醒 Agent 优先保存报告和产物。这个设计来自一次很具体的问题：前面分析得很深入，但最后几轮耗尽，没有把结果写入约定目录。

重复工具调用检测 ​

循环会记录最近一小段工具签名，也就是“工具名 + 参数”。如果同一个有副作用的调用反复出现，就停止任务并提示换一种方式。

只读搜索和团队状态轮询会被豁免，因为它们重复出现可能是正常行为。写文件和运行命令则更严格。

我一开始把阈值设得很低，结果正常的“写报告—读回—继续补充”也会被误判。后来才把策略按工具类型拆开。这个过程让我意识到，防死循环不能只看次数，还要理解工具的语义。

连续失败止损 ​

如果一整轮工具全部失败，并且连续发生三轮，MeiCode 会停止继续尝试。否则模型很容易围绕一个不存在的命令或无权限路径反复生成近似参数。

未知工具止损 ​

模型偶尔会“发明”一个没有注册的工具。偶发一次可以把错误回灌给模型，让它纠正；连续多轮都使用未知工具，则说明当前上下文或工具描述已经失效，应当结束任务。

上下文管理：最容易被低估的一层 ​

代码任务很快就会产生大量上下文：源码、命令输出、错误日志、工具参数、团队消息。如果不处理，最终一定会超过模型窗口。

MeiCode 没有把所有内容都简单截断，而是分成三步。

大结果先落盘 ​

工具输出过大时，内容会写入 .mewcode 下的 spill 文件，历史中只保留预览和文件位置。这样既不会丢失原始结果，也不会让一条命令输出占满整个上下文。

工具层本身还会限制单次回传大小。当前 MAX_RESULT_BYTES 是 8192 字节，超过后会按 Unicode 码点安全截断，避免从 UTF-16 中间切坏字符。

接近窗口时做摘要 ​

上下文管理器会保留最近一段对话，把较早内容压缩成摘要。摘要不是简单删掉旧消息，而是尽量保留已确认事实、失败尝试、关键路径和下一步。

MeiCode 没有依赖精确 tokenizer。它会参考最近一次 API 返回的 usage，再用字符数近似估算新增 Token。这个方案精度不是最高，但实现简单，而且能跨不同 Provider 工作。

这是一个我愿意在面试中主动说出的取舍：我知道它不完美，但当前目标是提前发现上下文风险，而不是做一个模型级 Tokenizer。

超限后自动恢复 ​

即使提前估算，Provider 仍可能返回上下文超限。主循环会触发强制压缩并重试当前轮，最多两次。

自动摘要如果连续失败三次，本次会话会停止自动摘要，但仍保留手动 /compact。这样做是为了避免“为了修复上下文，又进入另一个失败循环”。

权限不是一个 yolo 开关 ​

终端 Agent 可以写文件、执行命令，权限不能只靠提示词约束。

MeiCode 对用户提供 default、edits、plan 和 yolo 等使用模式。真正执行工具时，还会经过规则引擎、危险命令检查、路径围栏和人工确认。

工具调用的顺序是：

text
参数归一化
  → 权限规则匹配
  → 必要时向用户确认
  → Hook 拦截
  → 工具执行

分层规则 ​

权限规则可以来自用户、项目、本地和当前会话。会话规则优先级最高，同一层中 deny 优先于 allow。

用户批准一次操作时，可以选择：

  • 只允许这一次
  • 当前会话都允许
  • 写入项目规则，后续继续允许
  • 拒绝

命令会先做空白归一化，Windows 路径会统一分隔符，再参与匹配，避免同一条命令因为格式差异反复弹审批。

路径围栏 ​

多 Agent 模式下，每个成员都有 rootLock。写文件目标必须位于自己的 worktree，额外报告目录则通过 rootLockExtra 白名单开放。

仅限制 write_file 还不够，因为成员可以通过 run_command 间接写文件。所以命令围栏还会检查绝对路径和 .. 穿越。

这并不是操作系统级沙箱。它更像应用层的第二道防线。我不会把它描述成“绝对安全”，但它能挡住大量模型误操作，也方便在日志中解释为什么某次调用被拒绝。

多 Agent：难点不在 Promise.all ​

一开始看多 Agent，很容易觉得只是同时调用几次模型。真正做起来后，我认为至少要解决四件事：任务归属、上下文隔离、文件冲突和成员失联。

MeiCode 的团队由一个 Lead 和多个长期驻留成员组成。成员有独立历史，可以被重复分配任务，而不是执行一次就销毁。

text
Lead
  ├── research：调研和定位信息
  ├── implement：修改代码
  └── qa：运行测试和检查结果

共享：任务表、邮箱、产物目录
隔离：上下文、工具权限、Git worktree

为什么使用 Git worktree ​

如果多个成员直接修改同一个工作区，文件覆盖只是时间问题。为每个成员复制完整仓库又太重。

Git worktree 正好提供一个折中：每个成员拥有独立目录和分支，但仍共享同一个 Git 对象库。成员完成后先提交自己的改动，再由 Lead 合并回主分支。

发生冲突时，MeiCode 会中止合并并保留 worktree，让人可以继续处理，而不是强行选择一边。

Windows 上还有一个很具体的坑：worktree 中的 node_modules junction 如果处理不当，递归删除 worktree 时可能顺着链接影响主目录依赖。现在清理前会先识别并解链，避免把主项目的依赖一起清掉。

这类问题很难从 Agent 论文里学到，却是项目真正落地时会遇到的事情。

为什么还需要邮箱 ​

任务状态只能表示 todo、in_progress、done 或 failed，但团队协作还需要表达计划、审批和临时信息。

MeiCode 使用本地 JSONL 邮箱，约定了几种简单协议：

text
PLAN      成员提交执行计划
APPROVE   Lead 批准
DENY      Lead 拒绝
IDLE      成员完成任务并进入空闲
ERR       成员异常终止

邮件写入带文件锁，避免多个成员同时追加时损坏内容。

审批还有一个细节：成员只能接受本次 PLAN 发出之后的 APPROVE。否则邮箱中残留的历史批准消息，可能被下一项任务误用。

成员失联怎么处理 ​

成员执行异常时，任务会被标记为 failed，并向 Lead 发送 ERR。主循环在团队仍有进行中任务时，也不会因为模型输出一段普通文本就直接结束，而是要求继续检查任务状态或降级收尾。

这解决了一个真实现象：模型说“我会等待成员完成”，然后没有工具调用，普通 Agent Loop 会把这句话当成最终答案并退出。

Workflow 和多 Agent 不是同一件事 ​

Agent 适合动态决策，Workflow 适合固定阶段。MeiCode 的 Workflow 使用 .workflow.js 描述阶段：

js
export const meta = {
  name: 'feature-delivery',
  phases: [
    { title: 'research', prompt: '分析需求和相关代码' },
    { title: 'implement', prompt: '完成实现', agents: 2 },
    { title: 'verify', prompt: '运行测试并检查结果' },
  ],
}

每个 phase 有 pending、running、completed、failed 等状态，输出写入独立 artifact。阶段内部可以使用普通子 Agent，也可以交给团队中的驻留成员。

我的理解是：Workflow 决定“任务按什么阶段推进”，Agent 决定“当前阶段具体做什么”。把两者混成一个概念，系统会很难调试。

Provider 适配：先统一事件，再谈多模型 ​

MeiCode 支持 OpenAI 和 Anthropic 风格的协议。不同 Provider 的请求格式和流式事件并不相同，所以核心层只依赖一个很小的接口：

ts
interface Provider {
  readonly protocol: 'anthropic' | 'openai'

  streamChat(
    messages: ChatMessage[],
    options: {
      tools?: OpenAITool[]
      signal?: AbortSignal
    },
  ): AsyncGenerator<StreamEvent>
}

适配器负责把不同 SSE 数据转换成 text、thinking、tool_call、usage、done 和 error。Agent Loop 不需要知道上游返回了什么原始格式。

这样切换模型时，工具、上下文、权限和 TUI 都不需要跟着重写。

为什么核心没有直接使用 Agent 框架 ​

这个项目的一个选择是：核心执行层自己实现，没有直接建立在现成 Agent 框架上。

原因不是框架不好，而是我想把主循环、消息配对、权限顺序和失败恢复都握在自己手里。遇到 Provider 400、重复工具调用或者 Windows worktree 问题时，我能沿着完整链路定位，而不是先猜框架在哪一层做了转换。

代价也很明显：上下文管理、工具注册、事件流和测试基础设施都要自己维护。对于业务项目，如果只需要一个简单问答 Agent，我不会建议重新写一套运行时；但对 MeiCode 这种项目，底层能力本身就是要解决的问题。

我是怎么验证它的 ​

Agent 的输出有随机性，但外围系统仍然可以做确定性测试。

MeiCode 的测试覆盖了这些部分：

  • Agent Loop 的工具回流和停止原因
  • 文件、命令和代码搜索工具
  • 权限模式、审批缓存和危险命令
  • 上下文压缩、溢出落盘和消息清理
  • Memory、Skill、Hook 和 MCP
  • 子 Agent、团队任务和 worktree
  • Provider 流式解析
  • TUI 冒烟测试

写这篇文章前，我重新执行了：

bash
npm run typecheck
npm test

两项都通过。测试输出中会出现“命令不存在”“非法 Hook”“缺少 frontmatter”等警告，这些不是测试失败，而是在主动验证错误分支能否被正确识别。

这里我没有写一个夸张的准确率数字，因为当前测试主要验证运行时行为，不等于模型完成真实任务的成功率。后者还需要一套固定任务集和可重复的评估环境。

现在回头看，哪些地方还可以继续做 ​

MeiCode 已经能完成从单 Agent 到团队协作的完整链路，但我认为还有几个值得继续改进的地方。

统一参数校验 ​

工具已经声明 JsonSchema，不过执行前的运行时校验还可以进一步统一。目前很多参数检查分散在工具内部。如果加入统一 Schema Validator，错误信息和边界行为会更一致。

更系统的评估集 ​

单元测试能证明调度和权限逻辑正确，却不能直接说明 Agent 解决问题的能力。下一步可以准备一组固定代码任务，记录成功率、工具调用次数、耗时和 Token 成本。

更清晰的 Trace ​

现在已经有日志、事件和 Hook，但如果把一次任务整理成完整 Trace，就能直观看到每轮模型请求、工具耗时、压缩时机和失败原因。

团队调度策略 ​

当前主要由 Lead 根据角色分配任务。后续可以根据成员负载、工具权限和历史成功率做更细的调度，但我不会急着把调度算法复杂化。多 Agent 最先要保证的是隔离与可恢复，而不是角色越多越好。

权限边界继续下沉 ​

应用层路径围栏可以减少误操作，但高风险场景还应结合系统沙箱、容器或独立账户。权限系统需要明确自己的保护边界，不能把正则检查包装成绝对安全。

最后的复盘 ​

做 MeiCode 之前，我对 Agent 的理解更接近“模型加工具”。做完主循环、权限、上下文和团队协作后，我更愿意把它看成一个带不确定决策器的执行系统。

模型负责判断，工具负责行动，状态负责衔接，权限负责划边界，测试负责告诉我系统有没有真的完成。

最有价值的部分也不是接入了多少模型、预置了多少角色，而是那些看起来不显眼的处理：一次取消能不能正确收尾，一条历史审批会不会被错误复用，一个成员挂掉后任务会不会永远显示进行中，一次 worktree 清理会不会误删主目录依赖。

这些问题解决得越多，Agent 才越像一个可以工作的工程系统，而不只是一个效果不错的演示。
