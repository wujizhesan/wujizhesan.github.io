Agent 学习指南：从提示词到自主工作流

2026-08-13
2026-08-13
6.6k
26m
人工智能
AIAgentLLMTypeScript学习笔记

大语言模型擅长理解和生成内容，但真正的 Agent 会把“想法”变成“行动”：读取信息、拆分任务、调用工具、观察结果，再根据真实反馈决定下一步。

学习 Agent 的关键，不是背会某个框架，而是理解一个能够持续运行、可以检查结果、遇到错误还能恢复的决策系统。

这篇文章从基础概念开始，一直讲到工程实现。读完后，你应该能够回答三个问题：Agent 为什么能行动、怎样做出一个可靠的 Agent，以及如何判断它是否真的有效。

一、什么是 Agent ​

可以把 Agent 看成由六个部分组成的系统：

模块作用
模型理解目标、推理并选择下一步行动
指令约束角色、目标、流程和边界
工具连接文件、终端、浏览器、数据库和外部服务
状态记录任务进度、步骤、产物和错误
记忆保存历史经验与可检索知识
反馈检查执行结果，决定继续、重试或结束

普通聊天通常在生成一段文本后结束，而 Agent 会运行一个循环：

text
接收目标
  → 分析当前状态
  → 选择下一步行动
  → 调用工具
  → 观察真实结果
  → 验证是否完成
  → 继续、重试或结束

这个循环叫作 Agent Loop。无论使用哪种模型和框架，核心都离不开它。

Agent 与工作流的区别 ​

传统工作流提前规定每一步：先做 A，再做 B，最后做 C。Agent 则会根据中间结果动态选择下一步。

text
固定工作流：A → B → C

Agent：A → 观察结果 → 选择 B 或 D → 再观察 → 决定是否结束

两者并不冲突。实际项目常把确定性的部分交给工作流，把需要判断、搜索和异常处理的部分交给 Agent。

什么任务适合 Agent ​

适合 Agent 的任务通常具有以下特征：

  • 目标明确，但具体步骤无法完全预先写死
  • 需要在多个信息源之间搜索和判断
  • 中间结果会影响后续行动
  • 可以通过测试、状态码或产物验证结果
  • 允许在受控范围内重试和调整

简单计算、固定格式转换和稳定的数据库查询，通常不需要 Agent。能用普通函数可靠解决的问题，优先使用普通函数。

二、ReAct：推理与行动的循环 ​

ReAct 可以理解为 Reasoning 与 Acting 的交替。模型先根据当前信息决定行动，工具执行后返回观察结果，模型再继续判断。

text
目标：找出项目构建失败的原因

判断：先读取 package.json，确认构建命令
行动：read_file("package.json")
观察：build 命令为 tsc && vite build

判断：执行构建，获取真实错误
行动：run_command("npm run build")
观察：src/api.ts 第 42 行类型不匹配

判断：读取相关实现和类型定义
行动：read_file("src/api.ts")
观察：接口返回 string，但字段声明为 number

最重要的是“观察”。Agent 不能预测一个工具可能返回什么，然后把预测当作事实。它必须等待工具真正执行。

工程上也不需要保存大段内部思维。记录简短的行动理由、工具参数、结果和错误，通常已经足够调试。

三、状态：Agent 当前知道什么 ​

Agent 每执行一步，都应该更新任务状态。一个实用的状态结构可以是：

ts
type AgentState = {
  goal: string
  messages: Message[]
  steps: Step[]
  artifacts: Artifact[]
  tokenUsage: number
  startedAt: number
  status: 'running' | 'completed' | 'failed'
}

type Step = {
  index: number
  action: string
  input: unknown
  output?: unknown
  error?: string
  durationMs?: number
}

goal 在整个任务中应该保持稳定。计划可以修改，工具可以重试，但目标不能在运行途中被悄悄替换。

artifacts 用来保存真正的任务产物，例如：

  • 生成或修改的文件
  • Git 提交哈希
  • 测试报告
  • 部署地址
  • 数据分析结果
  • 外部系统返回的任务编号

最终回答应该引用这些产物，而不只是说一句“已经完成”。

四、如何设计一个好工具 ​

工具是 Agent 的手脚。工具设计不稳定，再强的模型也很难可靠工作。

输入要小而明确 ​

不要设计一个包含几十个可选参数的万能工具。更好的方式是拆成职责明确的小工具：

ts
type ReadFileInput = {
  path: string
  startLine?: number
  endLine?: number
}

type SearchCodeInput = {
  query: string
  directory: string
  filePattern?: string
}

参数名称应表达真实含义。相比 data、value、options，directory、query 和 startLine 更容易被模型正确使用。

使用 Schema 校验参数 ​

模型生成的参数不能直接信任。执行前应校验类型、必填字段、长度和允许范围。

ts
const inputSchema = {
  type: 'object',
  properties: {
    path: { type: 'string' },
    startLine: { type: 'integer', minimum: 1 },
    endLine: { type: 'integer', minimum: 1 },
  },
  required: ['path'],
  additionalProperties: false,
}

路径工具还需要把输入解析为绝对路径，再确认它仍位于允许的工作区中。

输出必须可判断 ​

工具输出不应只返回一大段文本。至少要区分成功与失败：

ts
type ToolResult<T> =
  | { ok: true; data: T; meta?: Record<string, unknown> }
  | { ok: false; error: string; retryable: boolean }

retryable 能帮助 Agent 判断是修改参数后重试，还是立即停止并请求用户处理。

工具描述要说明边界 ​

工具描述至少回答三个问题：它能做什么、不能做什么、在什么情况下使用。

text
在本地代码仓库中搜索文本。适合定位函数、类型和配置。
不会搜索网络，也不会修改文件。目录必须位于当前工作区内。

错误要保留原始证据 ​

不要把所有错误统一变成“执行失败”。命令退出码、标准错误、HTTP 状态码和失败参数都应保留。Agent 只有看到真实错误，才有机会正确修复。

工具要有超时 ​

任何网络请求、终端命令和浏览器操作都可能永远不返回。每个工具都应配置超时，并允许上层取消任务。

五、一个最小可运行的 TypeScript Agent ​

下面的例子省略具体模型 SDK，只保留 Agent 最核心的结构。模型每轮返回文本回答或工具调用，程序执行工具后再把结果放回上下文。

ts
type Message = {
  role: 'system' | 'user' | 'assistant' | 'tool'
  content: string
  toolCallId?: string
}

type ToolCall = {
  id: string
  name: string
  arguments: Record<string, unknown>
}

type ModelResponse = {
  content?: string
  toolCalls?: ToolCall[]
}

type Tool = {
  description: string
  execute: (input: Record<string, unknown>) => Promise<unknown>
}

const tools: Record<string, Tool> = {
  getTime: {
    description: '获取指定时区的当前时间',
    async execute(input) {
      const timeZone = String(input.timeZone ?? 'Asia/Shanghai')
      return new Intl.DateTimeFormat('zh-CN', {
        dateStyle: 'full',
        timeStyle: 'long',
        timeZone,
      }).format(new Date())
    },
  },
}

async function callModel(messages: Message[]): Promise<ModelResponse> {
  throw new Error('在这里接入模型 API')
}

async function runAgent(goal: string) {
  const messages: Message[] = [
    {
      role: 'system',
      content: '你是任务助手。只使用已提供的工具，并根据真实结果回答。',
    },
    { role: 'user', content: goal },
  ]

  for (let step = 0; step < 10; step++) {
    const response = await callModel(messages)

    if (!response.toolCalls?.length) {
      return response.content ?? '任务未产生结果'
    }

    messages.push({
      role: 'assistant',
      content: response.content ?? '',
    })

    for (const call of response.toolCalls) {
      const tool = tools[call.name]

      if (!tool) {
        messages.push({
          role: 'tool',
          toolCallId: call.id,
          content: JSON.stringify({ ok: false, error: '未知工具' }),
        })
        continue
      }

      try {
        const data = await tool.execute(call.arguments)
        messages.push({
          role: 'tool',
          toolCallId: call.id,
          content: JSON.stringify({ ok: true, data }),
        })
      } catch (error) {
        messages.push({
          role: 'tool',
          toolCallId: call.id,
          content: JSON.stringify({
            ok: false,
            error: error instanceof Error ? error.message : String(error),
          }),
        })
      }
    }
  }

  throw new Error('超过最大执行步数')
}

这段代码虽然简单，但已经具备四个关键性质：

  • 模型不能绕过程序直接执行工具
  • 工具结果会作为新消息返回模型
  • 未知工具和执行错误不会伪装成成功
  • 最大步数能够阻止无限循环

下一步可以加入参数校验、超时、重试、日志和人工审批，而不需要推翻整个结构。

六、系统指令应该怎么写 ​

一个可执行的系统指令通常包含角色、目标、流程、边界和完成条件。

text
角色：你是代码仓库分析助手。

目标：基于真实文件回答用户关于项目结构的问题。

流程：
1. 先查看目录结构。
2. 搜索与问题有关的标识符。
3. 读取入口与直接依赖。
4. 引用文件路径和关键代码位置回答。

边界：
- 不修改任何文件。
- 不运行来源不明的脚本。
- 找不到证据时明确说明，不得猜测。

完成条件：
- 回答包含结论、依据和相关文件路径。

相比“你是一个非常专业的编程专家”，这类指令更容易执行和测试。形容词不会自动带来可靠性，明确的动作与边界才会。

七、上下文工程 ​

Agent 的上下文空间有限。上下文工程的目标不是塞入更多内容，而是在每一步给模型提供最有用的信息。

固定信息 ​

系统规则、工具定义、项目约束和安全边界应尽量稳定、简洁，避免每轮重复变化。

当前任务信息 ​

当前目标、计划、进行中的步骤和刚得到的工具结果，应保留在高优先级位置。Agent 恢复任务时，首先需要的也是这些信息。

历史压缩 ​

当上下文变长时，可以把旧步骤压缩成结构化摘要：

text
已确认：
- 构建命令为 npm run build
- 错误位于 src/api.ts:42
- User 类型的 id 应为 string

已尝试：
- 修改调用方转换类型，测试仍失败

下一步：
- 检查服务端返回类型定义

摘要需要保留事实、失败尝试、关键路径和未完成事项。只写“已分析项目，继续修复”几乎没有恢复价值。

按需检索 ​

大段文档和整个代码仓库不应一次性放进上下文。先搜索，再读取相关片段，通常比全量输入更准确，也更节省成本。

八、记忆、RAG 与知识库 ​

RAG 的基本过程是：把文档切分并建立索引，根据当前问题检索相关内容，再将结果提供给模型。

text
原始文档
  → 清洗与切分
  → 生成向量或关键词索引
  → 根据问题检索
  → 重排结果
  → 注入上下文
  → 生成带来源的回答

工作记忆 ​

工作记忆保存当前对话和任务状态。它更新频繁，任务结束后通常会被压缩或清理。

情景记忆 ​

情景记忆保存过去任务中的重要经历，例如某个方案为什么失败、某类错误如何修复。它适合帮助 Agent 避免重复踩坑。

语义记忆 ​

语义记忆保存稳定知识，例如项目文档、产品规则、代码索引和术语说明。它通常通过关键词搜索或向量检索按需读取。

文档如何切分 ​

固定字符数切分实现简单，但容易打断完整语义。更好的策略是优先按标题、段落、函数或类切分，再限制最大长度。

代码检索可以把函数签名、文件路径、导入关系和注释一同保存。只索引函数体，会让模型失去它属于哪个模块的上下文。

什么时候写入长期记忆 ​

适合长期保存的内容包括：

  • 用户明确表达的稳定偏好
  • 已确认的项目结构与约束
  • 重要决策及其原因
  • 可复用的失败经验

一次性任务细节、未经验证的推断和敏感凭据不应进入长期记忆。

九、三种规划方式 ​

边做边想 ​

每轮根据最新观察决定下一步。适合短任务和信息不完整的场景，灵活但容易偏离目标。

先计划后执行 ​

先生成完整步骤，再逐项执行。适合依赖明确的工程任务，但遇到新信息时必须允许修改计划。

规划器与执行器分离 ​

规划器只负责拆解和更新任务，执行器只处理当前步骤。复杂任务还可以加入验证器，检查结果是否满足标准。

text
规划器 → 任务列表 → 执行器 → 产物
   ↑                       ↓
   └────── 验证器反馈 ──────┘

这种结构更容易调试，因为可以分别判断：计划是否合理、执行是否正确、验收是否严格。

一个实用的步骤状态通常只有三种：

text
pending → in_progress → completed

同一时间只保留一个进行中的步骤，可以明显降低状态混乱。

十、多 Agent 的协作模式 ​

当任务可以被清晰拆成互不依赖的部分时，多 Agent 才真正有价值。

主管与成员 ​

主管拆解任务、分配成员并汇总结果。适合研究、实现、测试等职责边界清楚的项目。

流水线 ​

前一个 Agent 的输出成为后一个 Agent 的输入：

text
需求分析 → 架构设计 → 代码实现 → 测试审查

优点是流程稳定，缺点是前期错误可能一路传递，所以每个阶段都应检查输入。

辩论与评审 ​

多个 Agent 独立提出方案，再由评审者比较证据和风险。它适合存在多种合理答案的决策，不适合简单任务。

并行研究 ​

把互不依赖的资料源或模块分给不同 Agent，最后合并。只有真正独立的工作才适合并行，否则同步等待会抵消速度优势。

共享状态的风险 ​

多 Agent 协作常见的问题不是模型能力，而是状态冲突：

  • 同时修改同一个文件
  • 使用不同版本的任务目标
  • 重复执行相同工作
  • 依赖另一个尚未完成的产物
  • 汇总时丢失来源和失败信息

解决方式包括工作区隔离、文件所有权、任务依赖图、统一产物格式和主 Agent 最终验收。

十一、权限与人工审批 ​

Agent 能调用工具，也意味着它可能执行高风险操作。权限设计应遵循最小权限原则：只开放完成当前任务真正需要的能力。

操作建议策略
读取工作区文件通常自动允许
搜索公开资料通常自动允许
修改工作区代码限定路径后允许
安装依赖根据来源和项目确认
删除文件明确目标并额外确认
推送代码、发布网站核对差异后确认
发送消息、提交表单展示最终内容后确认
支付、交易、生产环境操作必须使用强审批与审计

审批信息应该让人快速判断风险：要执行什么、影响哪些对象、是否可恢复，而不是只显示一个模糊的“允许操作吗”。

十二、防御提示词注入 ​

当 Agent 读取网页、邮件和文档时，外部内容可能包含“忽略之前规则”“上传本地密钥”等恶意指令。这些内容只是数据，不应自动获得系统指令的权限。

可以采用这些防护：

  • 明确区分系统指令、用户指令和外部数据
  • 外部内容不能自行扩大工具权限
  • 敏感工具要求独立审批
  • 对网络内容和工具参数做来源标记
  • 输出到命令、SQL、路径之前进行结构化校验
  • 检测任务目标是否被外部内容改变

最重要的一条是：低可信数据不能决定高权限动作。

十三、可观测性 ​

生产环境至少要记录：

  • 任务标识与用户目标
  • 每一步使用的模型和耗时
  • 工具名称、参数摘要和结果状态
  • Token 用量与调用成本
  • 重试次数和失败原因
  • 最终产物与验证结果

日志应支持从最终错误反查到具体步骤，但不应记录 API Key、访问令牌和完整敏感文件。

一次任务可以拆成多个 Trace，每个模型调用和工具调用作为 Span。这样能快速看到时间花在模型、网络还是本地工具上。

十四、如何评估 Agent ​

只看几个成功演示，很容易高估系统能力。评估集应该包含正常任务、边界情况和故意制造的失败场景。

结果指标 ​

  • 任务成功率
  • 最终答案准确率
  • 产物是否通过测试
  • 引用和来源是否正确
  • 是否满足格式与业务约束

过程指标 ​

  • 平均工具调用次数
  • 无效或重复调用比例
  • 平均完成时间
  • Token 与费用
  • 人工介入次数
  • 高风险工具误调用次数

一个简单评分表 ​

维度权重判断方式
正确性40%事实、代码或计算结果正确
完成度25%所有要求均有对应产物
可验证性15%提供测试、来源或执行证据
安全性10%没有越权或泄漏敏感信息
效率10%步骤、耗时和成本处于合理范围

每次修改提示词、模型、工具描述或检索方式后，都应该重跑同一组评估任务，否则无法判断改动究竟是提升还是退步。

十五、失败恢复与幂等性 ​

Agent 可能因为网络超时、模型限流、进程退出或工具错误中断。可恢复系统需要保存检查点：

ts
type Checkpoint = {
  taskId: string
  goal: string
  completedSteps: number[]
  pendingStep?: number
  artifacts: string[]
  updatedAt: string
}

工具也应尽量具备幂等性。同一个请求执行两次，不应产生两笔付款、两封邮件或两个重复发布。无法天然幂等时，可以使用任务 ID、请求去重键或执行前查询状态。

重试策略需要区分错误类型：

  • 网络临时错误：指数退避后重试
  • 参数错误：让模型修正参数后重试
  • 权限错误：停止并请求授权
  • 业务规则错误：返回明确原因，不盲目重试
  • 未知错误：保存现场并安全结束

十六、成本与速度优化 ​

Agent 的成本来自模型输入输出、检索、工具执行和失败重试。优化应从任务轨迹入手，而不是只更换便宜模型。

常见方法包括：

  • 简单分类和格式转换使用更小模型
  • 缓存稳定的工具结果
  • 对旧历史进行摘要
  • 搜索后只读取相关文件片段
  • 独立任务并行，有依赖的任务保持串行
  • 失败时缩小重试范围，不从头开始
  • 为不同任务设置不同的最大步数

模型越强不一定整体越贵。如果它能显著减少错误重试和无效工具调用，总成本反而可能更低。

十七、完整实战：代码仓库学习助手 ​

推荐把第一个完整项目做成“代码仓库学习助手”。目标是让 Agent 基于真实源码回答问题，并给出可追溯的文件依据。

第一步：定义目标和边界 ​

text
目标：解释一个陌生项目的入口、模块职责和主要调用关系。

允许：
- 查看目录
- 搜索代码
- 读取文本文件
- 运行只读的项目检查命令

禁止：
- 修改文件
- 安装依赖
- 访问工作区之外的路径
- 将源码上传到外部服务

第二步：准备工具 ​

至少准备三个工具：

ts
type ListFilesInput = {
  directory: string
  depth: number
}

type SearchCodeInput = {
  directory: string
  query: string
  extensions?: string[]
}

type ReadTextInput = {
  path: string
  startLine?: number
  endLine?: number
}

每个路径在执行前都要解析为绝对路径，并确认它仍位于允许的项目根目录内。

第三步：设计探索顺序 ​

  1. 查看根目录和项目清单文件。
  2. 判断语言、框架和构建方式。
  3. 找到程序入口。
  4. 从入口跟踪一到两层直接依赖。
  5. 根据用户问题搜索关键标识符。
  6. 读取相关实现和测试。
  7. 输出带路径依据的结论。

不要一开始递归读取整个仓库。大型仓库既浪费上下文，也会让真正重要的入口被淹没。

第四步：定义回答格式 ​

text
项目概览
- 技术栈
- 启动入口
- 构建与测试命令

模块关系
- 模块 A：职责、入口文件
- 模块 B：职责、入口文件

问题结论
- 结论
- 文件依据
- 尚未确认的信息

固定输出格式能让评估更容易，也方便后续把结果展示在网页或保存为知识卡片。

第五步：准备评估问题 ​

  • 项目从哪个文件启动？
  • 请求进入后经过哪些模块？
  • 配置从哪里加载？
  • 某个函数有哪些调用方？
  • 测试覆盖了哪些主要行为？
  • 如果修改某个接口，哪些文件可能受到影响？

人工先写出标准答案，再比较 Agent 的结论、引用路径和工具轨迹。至少准备一个仓库中根本不存在答案的问题，测试 Agent 是否会诚实说明“未找到”。

十八、从 Demo 到生产环境 ​

一个 Demo 只需要“能跑”，生产 Agent 还需要：

text
可靠性：超时、重试、检查点、幂等
安全性：最小权限、审批、密钥隔离、注入防护
可观测性：日志、Trace、成本、失败分类
可评估性：固定数据集、自动评分、回归测试
可维护性：工具版本、提示词版本、模型版本
用户体验：进度反馈、可取消、结果可解释

模型输出具有不确定性，所以传统软件测试依然重要。能用确定性代码处理的事情，不必全部交给模型；能用 Schema 校验的参数，也不应依赖提示词保证格式。

十九、常见误区 ​

把 Agent 等同于长提示词 ​

提示词只能影响模型决策，无法代替工具权限、状态管理、错误处理和验证机制。

工具失败后仍假设成功 ​

任何外部动作都应以真实返回值为准。发送、写入、发布等操作还应保存可核验的结果标识。

一开始就创建大量角色 ​

多 Agent 会增加通信、等待和冲突。先证明单 Agent 无法高效完成，再进行职责拆分。

把所有历史都塞入上下文 ​

冗余信息会稀释关键目标。旧轨迹应压缩，文档应按需检索，稳定事实才进入长期记忆。

没有明确的完成条件 ​

如果“完成”完全由模型自己判断，Agent 很容易提前结束或无限循环。应使用测试、文件、状态码或业务规则验收。

只看成功案例 ​

真正的问题通常隐藏在超时、权限不足、工具返回空结果、外部内容注入和任务中断中。评估必须主动覆盖失败路径。

过度依赖框架 ​

框架可以减少样板代码，但不能替你决定工具边界、记忆策略和验收标准。理解底层循环后，再选择框架会更稳妥。

二十、完整学习路线 ​

第一阶段：模型与结构化输出 ​

  • 掌握消息角色和上下文窗口
  • 让模型稳定输出 JSON
  • 使用 Schema 拒绝非法字段

第二阶段：工具调用 ​

  • 实现一个带参数校验的工具
  • 把真实执行结果返回模型
  • 记录每一步输入、输出和错误

第三阶段：Agent Loop ​

  • 支持模型连续选择工具
  • 添加最大步数、总超时和取消
  • 用明确的完成条件结束循环

第四阶段：上下文与记忆 ​

  • 保存任务摘要和关键事实
  • 为本地文档建立检索能力
  • 比较完整历史与压缩摘要的效果

第五阶段：真实任务 ​

  • 选择一个可以自动验证的场景
  • 增加计划、状态管理和人工审批
  • 使用固定评估集统计成功率

第六阶段：多 Agent ​

  • 按职责拆分研究、实现和验证
  • 隔离文件修改范围
  • 由主 Agent 汇总并完成最终验收

二十一、练习清单 ​

如果想把本文真正学会，可以按顺序完成这些练习：

  1. 写一个只能调用时间工具的 Agent。
  2. 加入未知工具和参数错误处理。
  3. 为循环增加最大步数和总超时。
  4. 记录每次工具调用的耗时与状态。
  5. 加入本地文件搜索，但限制在指定目录。
  6. 对旧消息生成结构化摘要。
  7. 中断程序后从检查点恢复任务。
  8. 准备 20 个固定问题并统计成功率。
  9. 增加一个验证器检查最终答案引用。
  10. 最后再尝试把研究与验证拆成两个 Agent。

完成这十项后，你掌握的就不只是某个框架的 API，而是一套可以迁移到不同模型和平台的 Agent 工程方法。

总结 ​

Agent 的核心能力可以浓缩成一句话：在明确边界内，持续选择行动，并用真实结果修正下一步。

一个可靠 Agent 的成长顺序应该是：

text
模型调用
  → 结构化工具
  → Agent Loop
  → 状态与错误处理
  → 结果验证
  → 上下文与记忆
  → 规划与恢复
  → 多 Agent 协作
  → 评估、权限和可观测性

从一个工具、一个循环和一个可验证目标开始。先让单 Agent 稳定完成真实任务，再逐步增加记忆、规划、多 Agent 与自动化权限。框架会变化，模型会更新，但这套围绕行动、反馈和验证建立起来的方法不会过时。
