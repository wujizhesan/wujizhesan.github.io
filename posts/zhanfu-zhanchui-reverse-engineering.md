站斧与战锤是一组经常会被误认为“重复目录”的项目。实际上，站斧工作区保存原始分析、接口兼容与重建过程，战锤则是在 Phase 1 之后形成的独立品牌分支。

这种分离很重要。逆向工作区需要持续对照目标、保留实验和兼容逻辑；品牌分支需要稳定、可维护并逐渐减少对原始实现的依赖。让一个目录同时承担两种职责，最终会导致无法判断哪些改动是对标修复，哪些是产品演进。

## 系统架构

```text
Electron 桌面端
  → Vue 3 / Element Plus 前端
  → Node HTTP 与 WebSocket 服务
  → SQLite 持久化
  → Chromium 店铺窗口与扩展
```

当前后端包含约 202 个路由处理器，覆盖认证、店铺、设备、订单、会员、云桌面、账单与系统设置等模块。前端主导航与懒加载路由合计 108 条，另有一批自动提取视图用于后续提升。

## 从 bundle 到可编辑页面

项目建立了组件提取、render 转模板、语义映射、路由接入与验证管线。自动转换可以快速让大量页面“编译并渲染”，但它有明确天花板：压缩变量名、运行时闭包和复杂 VNode 结构不会自动变成高质量业务源码。

因此页面被分为两条路径：

- 自动视图用于覆盖和侦察
- 主导航页面逐步提升为可维护的手写 SFC

这比一开始就声称“全部源码还原”更符合真实情况。

## 一次致命的路由问题

批量生成路由时，一百多个组件变量没有真正导入，构建阶段没有暴露全部问题，运行时却会触发 `ReferenceError`。最终把这些引用改为动态导入，并删除只用于调试的冗余路由，主界面才恢复稳定。

这个问题让我再次确认：路由表“数量很多”并不等于页面可达，必须在真实运行时逐条检查关键入口。

## 量化状态

目前项目具备：

- 前端构建 0 错误
- 202 个后端处理器
- JWT、加密响应兼容与 SQLite 持久化
- 22/22 API 与 SPA 端到端检查通过
- Windows 安装包与解包目录
- 特定 Dashboard 样本约 79% 视觉一致

最后一项只适用于特定元素和状态，不代表全站 79%。全页截图对比显示，不同页面与数据状态之间仍有明显差异。

## 下一步

站斧工作区将继续承担原版兼容与管线改进，战锤分支则专注独立品牌、图标、真实数据和交付质量。两者可以共享经过验证的基础设施，但不再互相覆盖。

这个项目最重要的产物，不只是一个安装包，而是对“逆向基线”和“产品分支”边界的认识。
