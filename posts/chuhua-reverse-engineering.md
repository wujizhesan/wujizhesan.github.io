初华是我做过的项目里，最能说明“先认清系统边界”重要性的一个。

最初看到的是一个电商采集浏览器，但拆开以后，它其实由定制 Chromium、主扩展、采集扩展和辅助扩展共同组成。浏览器负责运行环境和扩展加载，扩展负责界面、平台识别与业务动作，真正的数据又来自页面 DOM、脚本状态和远程资源。

## 四个组件，而不是一个程序

| 组件 | 作用 | 当前认识 |
| --- | --- | --- |
| 定制 Chromium | 浏览器内核与扩展运行环境 | 保留原技术路线 |
| 主扩展 | 产品入口与主要交互 | 已完成品牌层调整，仍需继续核验功能 |
| 采集扩展 | 平台识别与商品数据采集 | 远程依赖已本地化，核心链路已验证 |
| 辅助扩展 | 补充能力 | 已识别，等待更完整的功能检查 |

这个拆分避免了一个常见错误：把浏览器外壳、扩展和后端能力混成一个项目，然后用另一套技术做一个“看起来相似”的替代品。

## 远程依赖失效以后

采集扩展原本依赖外部脚本和远程注入资源。当远程服务不可用时，界面还在，但采集动作会在中间悄悄断掉。

我把平台脚本和浮动工具栏资源逐步转为本地加载，并重新检查 Manifest V3 下 content script、service worker 与页面脚本之间的时序。一次看似简单的配置删改，就曾破坏模块加载顺序，导致消息链没有明显报错却无法完成动作。

这让我形成了一条很实用的规则：扩展里的 `type: module`、注入时机和 service worker 生命周期不能凭感觉调整，每次修改都必须回到真实页面验证。

## 从消息链切换到 CDP 采集桥

扩展弹窗的一键采集链路多轮不稳定后，我没有继续在同一个故障点无限打补丁，而是把数据提取能力独立出来，建立了 Python CDP 采集桥。

它连接浏览器调试端口，读取当前页面，在明确的平台适配器中提取图片、属性、价格区间、SKU 与库存，再通过本地 HTTP 服务提供给前端调用。

目前已经验证的结果包括：

- 1688 商品详情中的图片与属性提取
- 阶梯价格区间解析
- SKU、价格与库存结构化输出
- 本地健康检查与采集接口

这不是换技术栈重做浏览器，而是把原有系统中最不稳定的一段消息链隔离出来，让采集能力可以单独观察、测试和复用。

## 一个绕不开的限制：扩展 ID

Chrome 扩展 ID 与签名私钥存在绑定关系。没有原厂私钥，重新打包后无法保持原 ID。对于依赖固定 ID 的组件，单纯“重新签名”并不能解决兼容问题。

初华最终采用开发者模式加载已解包扩展的方式，接受扩展管理页中的显示限制，同时保留功能验证所需的运行环境。这是一个技术约束下的明确取舍，而不是把失败结果包装成成功。

## 当前状态

初华已经完成平台资源本地化和一条可用的 CDP 采集链路，但主扩展、辅助扩展以及更多平台的新 DOM 仍需继续检查。淘宝和京东等平台还依赖有效登录态，不能用静态页面测试代替真实验证。

这个项目给我最大的收获，是学会把“浏览器能启动”“扩展已加载”“数据能采集”当成三件不同的事。只有三条链分别验证，系统才算真正可用。
