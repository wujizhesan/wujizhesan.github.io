Dr.JC 是一个水族商城方向的小程序项目，基础来自 CRMEB 生态。与桌面应用不同，它的主要困难不是拆解二进制界面，而是梳理多个版本的源码、后端接口和微信小程序构建流程。

项目同时存在 PHP 原版、Java 版前端、品牌化 uni-app 工程以及不同阶段的部署资料。如果不先建立版本关系，很容易把“源码存在”误认为“已经能够运行”。

## 当前技术路线

| 层 | 技术 |
| --- | --- |
| 小程序前端 | uni-app / Vue 2 |
| 目标后端 | CRMEB PHP |
| 参考实现 | Java 版 uni-app 与 PHP 原版 |
| 构建工具 | HBuilderX、微信开发者工具 |

前期已经捕获了九组页面与管理后台的接口响应，收集了安装文档和功能清单，并完成基础品牌配置。

## API 适配比换 Logo 更重要

Java 版与 PHP 版对接口前缀和部分调用约定不同。仅仅替换应用名称和图标，前端仍会把请求发送到不存在的地址。

当前已经对请求封装和公共工具中的 API 前缀进行了适配，并确认 PHP 后端的首页与登录端点存在。这只能证明最基础的协议方向正确，完整业务仍需要在编译后的小程序环境中验证。

## 为什么还不能说“完成”

Dr.JC 目前卡在 GUI 构建与部署链：

1. uni-app 工程需要先导入 HBuilderX。
2. 通过发行流程生成微信小程序产物。
3. 再由微信开发者工具导入和预览。
4. 最后验证域名、登录、商品、购物车和订单链路。

源码目录和配置已经准备好，但尚未完成上述全流程。因此我把它定义为“品牌与 API 适配完成，等待编译部署”，而不是一个已经交付的商城。

## 这个项目的价值

Dr.JC 展示了另一类逆向与迁移问题：有源码不代表有产品，有文档不代表能部署，有 API 响应也不代表前端能跑通。

真正的交付必须经过具体平台的工具链。对微信小程序来说，HBuilderX 和微信开发者工具不是最后随手点一下的步骤，而是运行环境的一部分。

后续我会先完成小程序构建与预览，再逐页核验接口，不会在编译尚未通过时扩展更多业务功能。
